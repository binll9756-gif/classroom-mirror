## 一、这些项目各自解决什么教育问题

### 1. THU-MAIC/OpenMAIC（重点）

**它解决的是"互动课堂内容的生产问题"。** README 原文：

> "OpenMAIC（Open Multi-Agent Interactive Classroom）是一个开源的 AI 互动课堂平台，能够将**任何主题或文档**转化为丰富的互动学习体验。基于多智能体协作引擎，它可以自动生成演示幻灯片、测验、交互式模拟实验和项目制学习活动——由 **AI 教师和 AI 同学**进行语音讲解、白板绘图，并与你展开实时讨论。"

教育问题拆解为三层：

1. **生产端**：做一节有互动、有提问、有板书的课，对教师是高成本劳动。OpenMAIC 把它变成"上传文档 → 几分钟出课"。
2. **消费端**：MOOC/录播是单向观看。OpenMAIC 用 AI 同学制造"有人在教室里"的社交在场感。
3. **形态端**：不只出幻灯片，还出**测验（quiz）、HTML 交互式模拟、项目制学习（PBL）**——把"听课"改成"动手"。

> 关键认知：**OpenMAIC 的用户是"学习者"，不是"教师"。** 它是一台"上课机器"，不是一台"训练教师的机器"。这正是我们项目的空位。

### 2. THU-MAIC/SimClass + MAIC-Core（论文 + 真实实现）

> **重要更正**：`SimClass` 仓库**没有代码**（只有 README.md + simclass.png，2025-02-05 后停更，**且无 LICENSE**）。但它的真实实现存在于同组织的 **`THU-MAIC/MAIC-Core`（Apache-2.0，2025-08-21 最后 push）**——我最初用 `git clone` 拿到空目录，改用 main 分支 zip 后成功下载并实读了代码。**所以 SimClass 这条线是有真实代码可学的**，见第二节 2.2。

**它解决的是"在线教育缺乏真实课堂人际互动"的研究问题。** 论文原文的三个 research questions：

> (1) Simulation Performance: How well can a multi-agent classroom simulate real-time teacher-student interactions?
> (2) Learning Experience: Can students in such environment experience a high sense of presence and learn effectively?
> (3) Group Behavior Observation: What behaviors may arise spontaneously in multi-agent scenarios?

实验规模：**400+ 名大学生在线使用，118 人完成全部章节；另有 48 人参加消融实验**；两门真实课程（TAGI 人工智能导论、HSU 大学生活技能）；主干模型 GLM-4，消融用 GPT-4V。

### 3. Hyan-Yao/instructional_agents

论文标题即结论：***Instructional Agents: Reducing Teaching Faculty Workload through Multi-Agent Instructional Design***（EACL 2026 主会接收，arXiv:2508.19611）。

**解决的是教师备课工作量问题**：基于 **ADDIE 教学模型**自动生成教学大纲、幻灯片、讲稿、评估材料。

值得特别注意的一点：它的 **Catalog 模式**可以传入"**学生档案 + 机构要求**"来约束生成——也就是**把学情作为输入**，这是同类项目里少见的做法（见 `README.zh.md` 功能表）。

### 4. AI-Tutor-Agent

**先说一句结论：这是五个项目里唯一"没有源码"的一个——但它恰好证明了低代码平台能走多远。**

`git clone` 下来的全部内容：`README.md`、`LICENSE`、`template.yml`（74KB，阿里云百炼/Dify 应用 DSL）、`prompts/`（**10 个 .md**）、`assets/`（14 张截图）、`data_samples/`（5 份电子课本 PDF）。**没有任何可执行代码。**

它的定位原文（`README.md:7-8`）：

> "一个基于**阿里云百炼**工作流编排与 RAG 技术构建的三方协同教育智能体。采用独创的'**输入-决策-执行**'三层架构，解决传统教育 AI '缺乏情感关怀'、'交互模式单一'与'直接给出答案'的痛点。"

**解决的是"三个角色各管一段"的问题**：学生端（启发式辅导 Heuristic Tutoring）、教师端（教案设计/习题生成）、家长端（**NVC 非暴力沟通** 家校沟通）。

**它最大的加分设计是 RAG 只吃自己上传的教材**，明确用"只用自己的资料"抑制幻觉——`prompts/system_rag_qa_engine.md` 就是这套约束。

**但它有两个必须引以为戒的问题**（对我们设计 Demo/说明书很重要）：
1. **它是"条件分支路由"，不是多智能体**：`template.yml` 里 11 个 LLM 节点 + 3 个 Classifier + 3 个 Judge，但节点之间**不对话、不共享状态**，一次请求只走一条分支。所谓"多 Agent"是**形式上的多节点**。
2. **它完全没有自动化评价闭环**——而这正是"微格教练"的核心。**11 个 LLM 节点的复杂度，换不来一个评价指标。**（另注：README 里"意图识别准确率 95%+""响应 5–20 秒"等指标无测量代码，未能验证。）

**解决的是"三个角色各管一段"的问题**：学生端（启发式辅导 Heuristic Tutoring）、教师端（教案设计/习题生成）、家长端（**NVC 非暴力沟通** 家校沟通）。

### 5. StudentTraineeCenter/edu-agent

**解决的是学生备考问题**。据其 `EduAgent_specification.pdf`（捷克学生毕业设计，STC/Siemens Mobility 合作）：

> 目标：分析学生备考需求，做一个 Web 应用，让用户上传自己的学习文档（PDF/DOCX/TXT），自动生成：关键词与摘要、卡片（问答对）、ABCD 交互测验、**根据用户表现的个性化学习计划**。

> 这是一个**单人 2 个月完成**的真实学生项目——对我们判定"大学生团队 MVP 工作量"是很好的标尺。

## 二、核心 Agent 架构（逐项目，带真实文件路径）

### 1. OpenMAIC —— 两套并存的架构，这是它最值得学的地方

OpenMAIC 内部**有两套完全不同的多智能体架构**，服务两种场景：

#### （A）课堂运行时：Director（导演）+ N 个角色 Agent —— 图编排

`lib/orchestration/director-graph.ts`（LangGraph `StateGraph`）文件头注释写得极清楚：

```
 *   START → director ──(end)──→ END
 *              │
 *              └─(next)→ agent_generate ──→ END
 *
 * Each request runs at most one director→agent cycle. The client serializes
 * multiple requests to drive multi-agent discussions. There is no maxTurns
 * cap — the topology is the bound.
```

三个关键设计（全部有源码支撑）：

1. **Director 是"选人 + 选动作"的调度器，不是说话的人**。`lib/orchestration/director-prompt.ts` 构造系统提示，输入是"可选 agent 列表（含 role + priority）+ 本轮已发言摘要 + 白板状态 + 对话摘要 + 学生档案"，输出是"下一个该谁说话、做什么动作"。
2. **单 Agent 时不用 LLM**：注释明确 "Single agent: pure code logic (no LLM). … Multi agent: LLM-based decision (with code fast-path for turn 0 trigger agent)." → **该省 LLM 调用就省**，这是工程品味。
3. **角色注册表带优先级**：`lib/orchestration/registry/store.ts` 定义 6 个内置 Agent：
   - `default-1` AI teacher，`role: 'teacher'`，`priority: 10`
   - `default-2` AI助教，`role: 'assistant'`，`priority: 7`
   - `default-3` 显眼包（class clown）、`default-4` 好奇宝宝、`default-5` 笔记员、`default-6` 思考者，均 `role: 'student'`，`priority: 4~6`

   每个角色有完整的 `persona`（教学风格/性格描述）+ `allowedActions`（白板动作 12 种 + 幻灯片动作 3 种）。**"角色 = persona + 权限 + 优先级"这个三元组，是可以直接照搬的设计。**

#### （B）PBL 生成流水线：Planner → Instructor → Simulator → Evaluator —— 四专职 Agent

`lib/pbl/v2/agents/` 下是 4 个职责分离的 Agent：`planner.ts`、`instructor.ts`、`simulator.ts`、`evaluator.ts`，配套 `lib/pbl/v2/prompts/` 下有 `evaluator-task.md`、`evaluator-milestone.md`、`evaluator-final.md`、`simulator-system.md`、`instructor-base-rules.md` 等独立提示词文件。

`evaluator.ts` 的头部注释直接解释了"**为什么要拆出独立评价 Agent**"，这段论述对我们的项目设计极有参考价值：

> Why a separate agent (not a tool on Instructor):
> - Different system prompts (reflection / report tone, not teaching). Same system prompt would fight itself.
> - Different output contract (narrative + JSON tail vs. conversational reply with optional tool calls).
> - Separate SSE call lets the client display "导师正在生成阶段报告" as a distinct phase.

而它的输出契约是 **"叙事文本 + JSON 尾巴（strengths/improvements/score、learned/performance/stars）"**——注意这句：*"a failed parse leaves the project untouched (the narrative is still shown — the LLM said useful things — just no structured payload to persist)"*。**这是"LLM 结构化输出失败时要优雅降级"的正确做法。**

另外它还有一个**学情内核**：`lib/pbl/v2/operations/kernel/` 下有 `proficiency.ts`（能力水平）、`engagement.ts`（投入度）、`progress.ts`、`task-completion.ts`——注意 `proficiency.ts` 只有 2 行，是 `export * from '@openmaic/generation/browser'` 的**兼容性 barrel 文件**，真实现在已抽成独立 npm 包 `@openmaic/generation`。

#### （C）Skill 体系：把"教学法"变成可插拔文件

### 2. SimClass（论文架构层）+ MAIC-Core（真实代码层）

论文第 3 节把课堂行为按教育学原则分成**四类**——这是它整个架构的地基：

| 缩写 | 全称 | 含义 |
|---|---|---|
| **TI** | Teaching and Initiation | 教师讲授 + 学生的反馈/想法 |
| **ID** | In-depth Discussion | 对齐、讨论、多轮问答，帮学生建构理解 |
| **EC** | Emotional Companionship | 鼓励学习、营造正向氛围、情感支持 |
| **CM** | Classroom Management | 维持纪律、组织破坏性行为、引导课堂内容 |

据此定义**两类 Agent**：

- **Teaching Agents**（权威传授方）
  - Teacher Agent **(TI, ID, EC, CM)**：按教学脚本展示材料、答疑
  - Assistant Agent **(ID, EC, CM)**：补充信息、参与讨论、**维持纪律与课堂连续性**
- **Classmate Agents**（同学，带鲜明性格）
  - Class Clown **(TI, EC, CM)** — 发起话题、活跃气氛
  - Deep Thinker **(TI, ID)** — 深度思考、提出挑战性问题
  - Note Taker **(TI, CM)** — 总结与分享笔记
  - Inquisitive Mind **(TI, EC)** — 频繁提问、激发讨论

> 括号里就是**每个角色的能力边界定义**。这个"角色 × 行为维度"的矩阵，比单纯写 persona 严谨得多，我们可以直接沿用。

#### 2.2.1 MAIC-Core 的真实代码架构（我亲自核对的部分）

**关键结论：SimClass 的"模拟学生"在代码里是真实存在的**，而且它是一个**"真人学生 + AI 同学"混合班**。

## 三、Agent 之间如何协作（这是最关键的对比维度）

我把它归成**四种协作范式**，每个项目占一种或两种：

### 范式 1：中央调度（Director / Manager）——OpenMAIC 与 SimClass

**共同点**：都有一个**隐藏的、不直接对学生说话**的调度 Agent，每轮决定"谁说话、说什么类型的动作"。

- **OpenMAIC**：`director-graph.ts` 用 LangGraph 实现，`START → director → agent_generate → END`，**一次请求只跑一轮 director→agent**，多轮讨论由前端序列化请求驱动。调度决策 = LLM 判断（但有代码快路径）。
- **SimClass 论文**：Manager Agent 定义为 `L: S_t → (a_t, f_t)`——输入课堂状态 `S_t = {C_t, H_t | R}`（已教内容 + 对话历史 + 角色集），输出"下一个说话人 + 下一个函数"。**触发机制**：一个动作执行后等待时间窗 τ，若用户发言或 τ 到点，则触发 Manager 重新决策。它的 Functions 体系分两类：
  - **Tutoring functions（只有教师能做）**：讲课、翻下一页
  - **Interacting functions（任何 agent 都能做）**
  - 论文明确说这些函数**是可插拔的**（"plug-in, allowing the addition of newly defined functions"）

> 对我们的启发：**"谁发言"和"做什么动作"必须解耦**。师范生试讲场景里，"学生该提问了"和"学生该走神了"是两种不同事件，而"谁来做"又是第三层决策。

### 范式 2：同伴上下文注入（Peer Context）——OpenMAIC 独有的巧思

多 Agent 对话最常见的失败是"**每个 Agent 都在重复打招呼和复述**"。OpenMAIC 的解法在 `lib/orchestration/summarizers/peer-context.ts`（全文 33 行），把"本轮其他人说过什么"压缩注入当前 Agent：

```
# This Round's Context (CRITICAL — READ BEFORE RESPONDING)
The following agents have already spoken in this discussion round:
- {name}: "{contentPreview}"
You are {name}, responding AFTER the agents above. You MUST:
1. NOT repeat greetings or introductions — they have already been made
2. NOT restate what previous speakers already explained
3. Add NEW value from YOUR unique perspective
4. Build on, question, or extend what was said — do not echo it
```

配套还有两个"共享工作记忆"压缩器：
- `lib/orchestration/summarizers/whiteboard-ledger.ts`：**白板台账**——把每个 Agent 画过什么记成结构化条目（`agentName` + 元素摘要 + id），再压缩成给 Director 看的清单。这是"多 Agent 共享一个可见产物"的干净实现。
- `lib/orchestration/summarizers/conversation-summary.ts`：把历史压成摘要，且**明确区分 `role:'user'` 是真人学生发言、`role:'assistant'` 是 agent 发言**（注释里写得很细，因为混淆会导致 Director 误判）。

### 范式 3：审议（Deliberation）——instructional_agents

`src/agents.py` 的 `Deliberation` 类（第 168 行起）：参数含 `agents[]`、`summary_agent`（默认取 `agents[0]`）、`max_rounds`、`instruction_prompt`、`input_files`、`output_format`；成员方法 `add_to_discussion()` / `format_discussion_history()` / `run(current_context, user_suggestion)`。

协作方式 = **阶段内多 Agent 讨论若干轮 + 由 summary_agent 收敛成结论**；**阶段之间**用 `current_context` 把上一阶段产出传下去。

> 也就是 **"阶段串行（ADDIE）+ 阶段内并行讨论 + 摘要收敛"**。这是最省事、最稳的多 Agent 模式，特别适合"教案分析→生成→评价→优化"这种有明确阶段的任务。

### 范式 4：异步流水线（队列）——edu-agent

API 收单 → 入队 → worker 里 `processors/registry.py` 分发到对应 processor → processor 调用对应 LangGraph Agent → 结果落库。Agent 之间**不直接对话**，通过数据库里的产物交接。

> 这是**最工程化、最适合长期维护**的形态，代价是没有实时互动感。

### 补充：OpenMAIC 对"多 Agent 翻车"的处理

它在 `eval/orchestration/scenarios/` 下准备了专门的评测场景：`premature-end.json`（讨论过早结束）、`answering.json`、`answer-content.json`，并配 LLM-as-judge（`eval/orchestration/judge.ts`、`answer-content-judge.ts`）。

> **这对我们极其重要**：不要假设多 Agent 会自然表现良好，必须为"翻车模式"建测试集。这句话可以直接写进我们说明书的"技术路线"里，显示工程成熟度。

## 六、为什么它们"适合教育场景"（不是复述，而是机制层面的原因）

这一节回答"为什么这些架构天然适配教育，而不是通用聊天机器人套壳"。

### 1. 教育的天然结构就是"多角色 + 固定职能"，这正是多 Agent 的适用前提

教育的角色分工是**先验存在**的：教师/助教/学生/教研员/家长。SimClass 的做法说明了一点——**不需要发明角色，只需要把教育里本来就有的角色 agent 化**（"we recognize representative class roles"）。这就是为什么多 Agent 在教育里不是噱头：**角色边界是行业既定的，LLM 只需要扮演，不需要设计组织架构。**

### 2. 教育有现成的、被学术界接受的评价体系——这给了 AI 输出"可验证的锚"

SimClass 用 **FIAS** 把课堂话语编码成 9 类（1 接受情感 / 2 表扬鼓励 / 3 采纳想法 / 4 提问 / 5 讲授 / 6 指令 / 7 批评 / 8 学生应答 / 9 学生主动发起），再算 4 个指标：**TT（教师话语比）、ST（学生话语比）、IDR（间接影响/直接影响比）、SIR（学生主动发起比）**。

**这意味着 AI 的教学评价不需要自己发明标准，而是可以对齐一个已经用了几十年的成熟量表。** 这是教育 AI 相对于通用 AI 的**结构性优势**：有 ground truth。

### 3. 教育场景天然容忍"结构化中间产物"——这解决了 LLM 输出的可靠性问题

OpenMAIC 的 Evaluator 用"叙事 + JSON 尾巴"，instructional_agents 用 `output_format: "md"`，edu-agent 把产物落库成卡片/测验/导图。**教育任务的产出本来就是结构化的**（教案有格式、试卷有题型、评课有维度），所以把 LLM 输出约束成 schema 不别扭。**而在通用聊天里做结构化输出，是在跟产品形态对着干。**

### 4. 教育有"过程数据"需求，天然需要状态与记忆——这不是过度设计

学习的价值在于**成长轨迹**而非单次结果。所以 OpenMAIC 要做阶段报告、edu-agent 要做"按表现自适应计划"、广西师大的系统要出"雷达图成长轨迹"。**在通用聊天里做长期记忆是加分项，在教育里是刚需**——因为教育评价的本质就是"增值性评价"。

### 5. 教育场景的失败成本可承受——这是它适合先落地的原因

OpenMAIC 的 PBL 流水线可以"评价 Agent 解析失败就不落库、叙事照常显示"。教育场景里，一次生成不完美是可接受的（老师会改），**但一次数据丢失/一次错误评价可能伤到人**。所以教育 AI 的工程重点不是"绝对正确"，而是**"可解释 + 可回退 + 人可干预"**——这与"多 Agent + 中间产物可审查"的架构天然契合。

### 6. 但反过来看：这五个项目**共同的盲区**，就是我们的机会

- 它们的用户都是**学习者**或**教师的日常事务**；
- 它们的 AI 都在**扮演"更懂的人"**（AI 老师、AI 助教、AI 导师）；
- **没有一个让 AI 扮演"更弱的、会犯错的人"，来训练"未来要教人的人"。**

**师范教育的特殊性恰恰在于：它的"学生"（师范生）将来要成为"教师"。训练一位教师的最高效方式，不是给他答案，而是给他一个会犯错、会质疑、会走神的学生。**

## 七、目前高校比赛中少见、但真正有教育价值的创新点（重点）

以下 8 条，每条都附"为什么现行项目没做/做得浅"，以及"教育价值在哪里"。

### 创新点 1：反事实学生（Counterfactual Students）——AI 不装懂，而是装不懂

**现状**：OpenMAIC 的四类 AI 同学是"显眼包/好奇宝宝/笔记员/思考者"——都是**良性角色**，扮演的是"活跃气氛的好同学"。AI-Tutor-Agent 的 `student_oral_practice_partner` 是"陪练"，但不承担认知冲突。

**我们的做法**：虚拟学生携带**学科典型迷思概念**（如数学："从关键词选运算"；科学：见 OpenMAIC `references/subjects/science.md` 的 "Common misconceptions to select by subject"），并且**会坚持错误理解、会拒绝被说服**。

**教育价值**：师范生最缺的能力是**诊断性教学**（diagnostic teaching）——从学生的错误回答里反推他的认知结构。与"正确学生"对话训练不出这个能力。

**可行性**：极高。种子知识库已有 MIT 授权的现成文档。

---

### 创新点 2：把 **FIAS 的 IDR（间接/直接影响比）** 变成师范生的训练 KPI

这是我这次调研里**最硬的一个发现**。SimClass 论文 Table 2 实测数据：

| 课堂 | TT | ST | **IDR** | SIR |
|---|---|---|---|---|
| SimClass（AI 教师）TAGI | 0.816 | 0.184 | **0.058** | 0.896 |
| SimClass（AI 教师）HSU | 0.863 | 0.137 | **0.124** | 0.917 |
| **专家人类教师 ET** | 0.771 | 0.229 | **1.473** | 0.121 |
| **新手人类教师 NT** | 0.826 | 0.174 | **0.885** | 0.106 |

**读法**：AI 教师的 TT/ST（话量分配）已经接近人类，但 **IDR 只有 0.058，而专家人类教师是 1.473——差 25 倍**。也就是说：**AI 很会"讲"，几乎不会"引导"**（接受学生情感、表扬鼓励、采纳学生想法、提问——这四类正是 FIAS 的 1~4 类）。

**结论可以这样立论**：*"AI 尚不能替代教师的间接引导能力；那么与其让 AI 去当老师，不如让 AI 当学生，把'间接引导'这项人类核心竞争力训练到位。"*

**教育价值**：IDR 是国际通行的课堂话语分析指标；用它当 KPI，既**客观可测**，又**正好命中师范生的能力短板**，还能直接支撑比赛要求的"量化数据、对比成效"。

> ⚠️ **必须同时遵守的纪律**（我在整理编码规则时才发现这个陷阱）：FIAS 四指标中只有 **IDR** 纯反映教师行为；**TT/ST 受"我们把 AI 学生设定得多爱说话"影响，SIR 更直接由设计参数决定**。所以 **TT/ST/SIR 只能作情境描述，不得作为师范生能力提升的证据**。详见 `09_教学知识资产（FIAS规则卡+迷思概念库）.md` 第 1.5 节。

**可行性**：高。编码用 LLM + 固定 9 类标签即可，无需多模态。

---

### 创新点 3：**"教案—实施—评价"三方一致性诊断**（Constructive Alignment 建构一致性）

**现状**：广西师大的系统能指出"你花大量时间讲软件操作，偏离了培养实操能力的核心目标"——**但这是一句自然语言结论，不是结构化检测**。OpenMAIC 有 `k12-core-literacy-planning/SKILL.md` 提到 "assessment alignment"，但那是**生成时**的约束，不是**诊断**。

**我们的做法**：从教案抽取"教学目标（ABCD 要素）→ 教学活动 → 评价/练习"，从试讲记录抽取"实际发生的教学行为"，做**三列对齐矩阵**，标出：
- 目标写了但整节课没被教到（落空目标）
- 教了但和任何目标都不对应（游离活动）
- 有目标但没有任何检测手段（不可评目标）
- 评价的认知层次低于目标的认知层次（如目标"分析"却只用"记忆"型提问检测）

附完整示例（初中数学·负负得正）——**如果我们的 Demo 里出现这样一张矩阵，"专业感"会瞬间拉满，而且评委一看就懂。**

**教育价值**：建构一致性是师范生最常犯且最少被检测的错误。这可能是**整个方案里最具原创性、最容易讲清楚的一个点**。

**可行性**：中高。本质是"两份结构化数据的对齐比对"，可用 JSON 结构化输出 + 程序化比对，不依赖 LLM 自由发挥（更可控）。

---

### 创新点 4：**教师等待时间（wait time）训练**

**现状**：所有项目都不测这个。

**背景**：教育学经典结论——教师提问后的等待时间从 1 秒延长到 3 秒以上，学生的回答长度、复杂度、主动参与显著提升。

**我们的做法**：AI 学生**故意卡住/犹豫**（"呃……老师，是……先乘吗？"），系统计时师范生**等了多久、有没有抢答、有没有直接给答案**。指标 = 平均等待时间、抢答率。

**教育价值**：极具体、极可训练、几乎零技术难度（就是计时器 + 事件流），却有明确教育学依据。**投入产出比最高的一条。**

---

### 创新点 5：**叫答公平性（equity）检测——"被忽略的学生"**

**做法**：系统记录师范生叫答了哪些"学生"。若某个虚拟学生整节课 0 次被叫到（尤其"低参与度"的那位），则在报告里把该学生**灰色高亮**并提示："这位学生在你的课上被忽略了 8 分钟。"

**现状**：无人做。

**教育价值**：直接对应师德与教育公平（也是师范专业认证的关注点），且**伦理上极其正当**——它不是在评价学生，而是在提醒教师。演示时视觉冲击力强，一句话就能让评委记住。

---

### 创新点 6：**"AI 拒绝替你想"的反思设计**

**现状**：所有项目都在"帮用户生成"（生成课程、生成教案、生成计划）。**AI 越强，人越懒**——这是教育 AI 的异化风险。

**我们的做法**：反思环节**不生成反思**，只做苏格拉底式追问：*"你说想加情境，但你试讲时其实试过一次情境——还记得学生当时的反应吗？"*。追问 3~5 轮，反思报告最后由师范生自己写完、自己签字。

**教育价值**：这是教育理念层面的亮点，也是**伦理答辩时的护身符**——当评委问"AI 会不会让学生变懒"，我们正好有答案。

**可行性**：极高（提示词工程 + 对话记录回查）。

---

### 创新点 7：**可解释评价——每条结论都带"原文证据"**

**做法**：评价报告里每一句判断都必须挂证据锚点，点击即高亮试讲原文片段：
> "你在 3 分 12 秒说：**'好，那这个大家记住就行，考试要考'** —— 这属于 FIAS 第 6 类【给出指令】，且用'考试要考'替代了对原理的解释。"

**现状**：OpenMAIC 的 Evaluator 输出"叙事 + JSON 尾巴"，但没有强制证据引用；edu-agent 的 spec 里明确批评通用 AI "hallucination、ozdrojování（无出处）"。

**教育价值**：教研活动的基本规范就是"用证据说话"。同时它解决 AI 评价最大的可信度问题——**老师无法反驳、也无法申诉一个没有证据的分数**。

---

### 创新点 8：**以"教学行为变化"作为成效证据，而不是满意度问卷**

**现状**：绝大多数参赛项目用"用户满意度""愿意继续使用"当成效。

**我们的做法**：同一份教案、同一位师范生，**训练前后两轮试讲**，对比：
- IDR 从 0.12 → 0.58
- 平均等待时间 1.1s → 3.4s
- 被忽略学生 0 → 0
- 记忆型提问占比 5/6 → 2/7

**教育价值**：比赛章程明确要求提交"**量化数据、用户反馈、对比成效**"。行为指标变化比满意度问卷硬得多，也更容易在决赛答辩时经得住追问。

---

## 八、外部实证证据：这个方向"值不值得做"，文献已经给了答案

> 这一节是我们**说明书第一章**的弹药库，也是答辩时最难被问倒的部分。所有结论都附出处。

### 8.1 已经有人做了，但**没有一个研究证明了"普遍有效"**

| 研究 | 设计 | 结论 |
|---|---|---|
| 宛平、顾小清，《基于大模型多智能体的模拟课堂实训能提升师范生的教学效能感和表现吗？》，《现代教育技术》2025, 35(10): 60-69，DOI 10.3969/j.issn.1009-8097.2025.10.007 | **单组实验、n=27、无对照组** | 提升了教学效能感，**但**：① 课堂管理与学生参与效能感**待加强**；② 师生互动**以师范生为中心，学生主动性不足**；③ 教学策略转化待提升。设计框架三要素：**虚拟学生 / 关键事件 / 教学设备** |
| Liu B., Yang Y., Xu G.（香港教育大学 LTTC），*GenAI-Empowered Virtual Micro-teaching Training System for Preservice Teachers*, Springer LNCS 16433, pp.232-241（BESC 2025） | metaverse/VR + GenAI 模拟学生应答 + 生成教学反馈；师范生"**应答式教学 → AI 反思 → AI 修订**"迭代 | 动机与我们**完全一致**（指出真实同伴角色扮演无法复现真实学生的认知水平、知识掌握进程与反馈）。**摘要中没有任何量化效果数据**，只称在香港/大湾区中小学语文读写建立"impact cases" |

**读法**：方向被学术界认可，**但效果证据薄弱**。这既是风险（不能吹），也是机会（**谁能把"效果"做扎实，谁就有真贡献**）。

### 8.2 关键量化证据：什么有效、什么无效

| 研究 | 设计 | 效应量 / 结论 |
|---|---|---|
| **Zhakpayev 等 2026**, IJLTER 25(6)，哈萨克斯坦 | n=86，Llama 3.1 扮演"**学困生**"Telegram 机器人 vs 对照组，持续**一学期** | **讲解表现 d=0.90（强）**；PCK d=0.35（弱）；**物理教学自我效能感 d=0.20（微弱、不定论）** |
| **Zhang C. 等 2026**, *Teaching and Teacher Education* 172: 105355（上海师大/北师大/宁波大学等） | 准实验：**AI 反馈组 n=20 vs 人类教师反馈组 n=19** | 两类反馈都能显著提升效能感（学生参与/教学策略/课堂管理三域），**但教师反馈在"可信度与有用性"上显著更高**；认知负荷影响对反馈有用性的感知 |
| Mikeska 等 2023, *Journal of Teacher Education* | **LLM 之前的**模拟课堂/TeachLivE 路线 | 对"引导论证式讨论"这一核心教学实践有统计显著提升 |

**三条可操作结论（直接决定我们的技术路线和宣传口径）**：

1. **行为表现能显著提升（d=0.90），自我效能感和 PCK 提升很弱（0.20~0.35）** → **我们要把 KPI 建在"教学行为"上，不要建在"感觉"上。** 这正是我前面推荐 IDR / 等待时间 / 叫答公平性的实证依据。
2. **AI 反馈不如人类导师反馈"可信、有用"** → **我们的定位必须是"人类导师之前的预训练场"，而不是"取代导师的裁判"。** 系统设计上要显式做"**AI 报告 → 人工导师复核/批注**"的人机协同（这同时命中评分标准的"人机协同高效"与"合规与伦理"）。
3. **一学期的持续使用才换来 d=0.90** → 我们做的是**一次 5 分钟 Demo**，绝不能宣称"几次训练就能提升教学能力"。**正确的宣传口径是"把训练成本从 1 次真实试讲降到 0 成本反复试错"**，而不是"提升 N 倍教学水平"。

### 8.3 反方证据：模拟学生"假"在哪（这五条就是我们的技术验收清单）

Martynova 等，BEA 2025（ACL），*Can LLMs Effectively Simulate Human Learners?*（https://aclanthology.org/2025.bea-1.8/ ）通过教师访谈发现，现有 LLM 模拟学生有**五类真实性缺陷**：

1. **真实性不足**（不像真学生）
2. **语言复杂度偏高**（说话像老师/像论文，不像 K12 学生）
3. **缺乏情绪**
4. **不自然地专注**（永远在听、永远配合——**这就是"乖学生"问题的学术表述**）
5. **逻辑不一致**（前后矛盾，忘记自己刚才答错了）

> 🎯 **这五条 = 我们虚拟学生引擎的验收标准**。而且每一条都能在 Demo 里当场演示"我们解决了"：
> - 语言复杂度 → 学生台词受**年级词表/句长**约束
> - 不自然专注 → 有**走神/沉默/被点名才回神**的行为
> - 逻辑不一致 → 维护**每个学生的认知状态机**（"我前面答错了，所以现在我还是不懂"）
> - 缺乏情绪 → 有**挫败/兴奋/焦虑**状态并影响发言
> - 真实性 → 错误来自**学科迷思概念库**，而非随机胡说

**这是把"文献指出的缺陷"直接变成"我们的功能清单"——评委很难挑刺。**

### 8.4 最接近的已有工作（⚠️ 必须主动提及并划清界限）

> **先做一个诚实纠正**：本人在 `04` 文件中曾写"反事实学生几乎无人做"。**这个说法过强，必须收回。** 学术界已经有明确先例（见下 **Student GPT**）。**正确的表述是**："**'让 AI 扮演带迷思概念的学生'这一机制已被单点验证；但把'反事实学生 → FIAS 行为量化 → 反思 → 教案自动迭代'做成面向师范生的完整闭环产品，尚无公开工作。**" 如果评委读过文献而我们过度声称"原创"，那是致命伤。

| 已有工作 | 它做了什么 | 与我们如何划界 |
|---|---|---|
| **Student GPT / Student ChatGPT**（Zhuang & Zhang, *IJAIED* 2025, DOI 10.1007/s40593-025-00519-0） | **定制聊天机器人扮演"比例推理有迷思概念"的初中生**，做互动质性分析（情感/交流/技术三维） | 🔴 **这是"反事实学生"的直接先例，必须引用。** 它的产出是**质性分析**，不是师范生训练系统；没有行为量化、没有教案闭环、没有评价量规。**我们的差异在"闭环 + 量化 + 师范培养对接"，不在"让 AI 犯错"这个点本身** |
| **EduAgent**（github.com/EduAgent/EduAgent，NAACL 2025 论文实现，43★，**License 显示 NOASSERTION，未核实**） | 论文《Simulating Classroom Education with LLM-Empowered Agents》的**"生成式学生智能体"官方实现**，与 SimClass 同一篇论文 | ⚠️ **这是 SimClass 那条线的另一个代码入口**（此前我只找到 MAIC-Core）。可对读，但许可未核实，**引用前必须自行核对 LICENSE** |
| **TeachTune**（arXiv:2410.04078） | 面向**教师**的工具：创建模拟学生 + 观察 PCA↔模拟学生自动对话以审查自适应性；30 名科学教师组间实验，使用组**任务负荷更低、学生画像覆盖率更高** | **与我们最像的工具类工作。** 它的重心是"**配置与检查模拟学生**"（authoring + inspection），我们是"**在对抗中训练 → 行为量化 → 反思 → 教案迭代**"的闭环，且评价锚定 FIAS 与建构一致性 |
| **Classroom Simulacra**（github.com/songlinxu/ClassroomSimulacra，CHI 2025，**CC0-1.0**） | 在线教育中构建"情境化学生生成智能体"模拟学习行为 | 研究复现价值高（CC0 最宽松）；但定位是**行为模拟研究**，非教师训练产品 |
| **模拟学生真实性三路线对比**（AIED'26, arXiv:2604.04361） | 比较 Fine-tuning / Multi-agent / DPO 三种路线；n=8 师范生与研究者访谈 | **三条路线均优于 few-shot**；微调版"真实但**限制学生思维的延展**"；多智能体/DPO 会生成**显式推理**。→ **我们的选型依据**：MVP 用提示词+状态机（等同 few-shot+规则，最省），若做真实感再考虑 DPO |
| **Li Ming-Fen 等 (2025)**，*Interactive Learning Environments*, DOI 10.1080/10494820.2025.2591238 | ChatGPT-4o + **零样本思维链**生成多样化学生反应（含追问与偶发误解），n=29 师范生，混合方法 | ✅ **一个正向结果**：显著提升**教学对话质量（接近有经验教师水平）**与自我效能感。单组小样本，需谨慎外推——但它说明"模拟学生 → 对话质量"这条链是能被证实的，**正好是我们的主打指标** |
| **Simulating Students with LLMs 综述**（arXiv:2511.06078） | 主题综述 | 结论：LLM 胜过规则系统，但**算法偏见、评估可靠性、与教育目标一致性存疑**。→ 直接支撑我们"可解释 + 可审计 + 可申诉"的设计理由 |
| **SimClass**（arXiv:2406.19226 / NAACL 2025） | 见本文档第二、三节 | 方法论引用（FIAS + 角色×行为矩阵） |

**设计层面的四条建议**（来自上述文献的共识，可直接写进说明书）：
1. **引入多样化人格**（防"全班一个性格"）；
2. **建模知识建构过程**（不是"答对/答错"二元，而是理解如何逐步形成）；
3. **促进学生主动提问**（这正是"学生主动性不足"这一实证短板的靶向解法）；
4. **给推理而不是只给答案**（多智能体/DPO 路线的优势所在）。
