# V1.0 功能范围冻结与分工

> **这份文档的作用**：把"最终要做成什么样"一次性定死，然后据此分工。
> **冻结日期**：2026-09-21　**目标提交**：2026-10-18 18:00（还剩 26 天）
> **规则**：本文件一旦冻结，**新增功能需要走第 8 节的变更流程**，不允许口头加需求。

---

## 0. 一句话说清产品最终形态

> **师范生上传教案 → 系统生成 3 个"带着迷思概念来上课"的 AI 学生 → 师范生试讲、AI 学生提问/答错/坚持/走神 → 系统用 FIAS 给每句话编码、用代码算出教学行为指标 → 出带原文证据的诊断报告 → 师范生自己写反思、改教案 → 第二轮试讲 → 两轮对比看有没有进步。**

**核心价值**：把师范生的试错成本降到接近零，并让"有没有进步"有数字可看。

## 1. V1.0 必做功能（11 项，逐项带验收标准）

> 验收标准必须是**可当场验证的**，不许写"体验良好"。

### F1 教案上传与解析
- **做什么**：上传 PDF 或纯文本教案 → 解析出：教学目标 / 重点 / 难点 / 学情假设 / **迷思概念** / **设计薄弱点**
- **验收**：上传一份初中数学 PDF，**60 秒内**出结构化结果，含 ≥3 条迷思概念假设
- **不做**：PPTX、OCR、图片教案

### F2 生成 3 个虚拟学生
- **做什么**：按原型生成 3 个差异化学生（迷思型 / 沉默走神型 / 过度积极型），每个带：预设迷思概念、参与度、语言约束、认知状态
- **验收**：**同一个 seed 生成同一批学生**（可复现）；三人的迷思概念不同

### F3 实时试讲对话
- **做什么**：师范生输入话语 → AI 学生实时回应（**真模型生成**，不再是模板）
- **验收**：连续对话 10 轮内，出现 **≥1 次答错、≥1 次质疑或超纲、≥1 次走神/沉默**

### F4 学生认知状态跨轮一致 ★
- **做什么**：状态由**代码**维护；学生答错后**不被追问就变懂**
- **验收**：S1 在第 3 轮答错后，第 8 轮仍表现为"未理解"（**不得自行变聪明**）
- **说明**：这是全项目最难的一处，也是最容易被评委追问的一处

### F5 关键事件（2 个手动按钮）
- **做什么**：老师端一个"走神"按钮、一个"集体沉默"按钮，点击后触发
- **验收**：点击后界面出现对应事件，并记入事件流
- **砍掉的**：不做"智能判断时机"

### F6 逐句 FIAS 编码
- **做什么**：每一句课堂话语打上 FIAS 九类标签（1~9）
- **验收**：输出"每句一个标签"的序列；抽样与人工标注可比对
- **说明**：可先用规则分类器 + 抽样人工校验；**不追求全自动准确**

### F7 指标计算（★ 必须由代码做）
- **做什么**：IDR / TT / ST / SIR + 平均等待时间 + 抢答率 + 叫答分布 + 提问层次分布
- **验收**：**同一份对话重复计算，结果完全一致**（可复现）
- **禁令**：**不许让模型算指标**

### F8 评价报告（带证据）
- **做什么**：雷达图/评分 + 每条结论挂 `evidence_turn_ids`，点击可跳回原文高亮；IDR 旁显示"专家人类教师 1.473"对照刻度
- **验收**：**无证据的结论数量为 0**

### F9 第二轮试讲 + 两轮对比
- **做什么**：同一份教案的修订版再讲一次（学生原型与参与度一致）→ 出对比表
- **验收**：显示 IDR / 等待时间 / 抢答率 / 记忆型提问占比 / 被忽略学生数的**前后变化**
- **说明**：这是"闭环"的唯一证明，**绝不能砍**

### F10 数据落库 + 可重算
- **做什么**：事件流只追加不修改；指标为派生数据，可随时重算
- **验收**：从事件流重算两次结果一致；能回答"这个分数怎么来的"

### F11 公网部署 + 测试账号 ★
- **做什么**：评委能用别人的电脑登录并操作
- **验收**：**用手机热点 + 别人的电脑各登录一次成功**；准备"载入历史会话"兜底入口
- **说明**：这是比赛明确的配套材料，**不给直接丢分**

## 2. V1.0 明确不做（写下来是为了防止加需求）

| 不做 | 理由 |
|---|---|
| 语音（TTS / ASR） | 现场风险高，不增加教育价值 |
| 数字人 / 头像动画 | 同上；且 Live2D 商用要签约 |
| 多学科 | 先做通初中数学一个课时，**别对外说"全学科通用"** |
| 反思教练独立 Agent | 用**固定追问模板 + 关键片段回填**即可，理念（不代写）保留 |
| 教案 patch 自动落版 | 只出**建议清单 + 理由**，人自己改 |
| 跨会话成长曲线 | 只做"两轮对比" |
| 学科教研员 Agent | 二期 |
| 移动端 / 小程序 | 桌面 Web 够用 |
| 视频/眼神分析 | **刻意不做**（隐私与伦理成本） |

## 3. ★ 数据契约（让前后端能真并行的关键）

**这三段 JSON 就是前后端的接口。后端不要改字段名，前端照着做即可——这样前端不必等后端。**

> 契约已经由现有代码固化：`kj/store.py`（turn / compare）、`kj/fias.py`（metric）。**改字段名等于改契约，必须走变更流程。**

### 3.1 turn（事件流的一条）

```json
{
  "idx": 1,
  "speaker": "teacher",           // teacher | student
  "name": "师范生",                // 或学生名：小林 / 小周 / 阿豪
  "text": "(-3)×(-2) 等于多少？",
  "fias": 4,                      // 1~9；走神等行为事件为 null（不进九类）
  "wait_ms": 3200,                // 教师提问后下一位发言者的等待时长
  "target": "小林",                // 教师点名指向的学生（可为 null）
  "behavior": ""                  // 如 "答错并坚持" / "走神" / "抢答"
}
```

### 3.2 metric（一次试讲的指标，全部由代码计算）

```json
{
  "TT": 0.519, "ST": 0.481,
  "IDR": 1.333, "SIR": 0.333,
  "teacher_questions": 4, "answered_questions": 4,
  "avg_wait_s": 3.5, "rush_rate": 0.0,
  "call_distribution": { "小林": 2, "小周": 1, "阿豪": 1 },
  "ignored_students": [],
  "bloom_distribution": { "记忆": 1, "理解": 3 },
  "memory_question_ratio": 0.25
}
```

### 3.3 compare（两轮对比，前端直接照着渲染）

```json
[
  { "label": "IDR 间接/直接影响比", "a": 0.143, "b": 1.333, "delta": 1.19,  "trend": "↑ 改善" },
  { "label": "平均等待时间(秒)",   "a": 0.9,   "b": 3.5,   "delta": 2.6,   "trend": "↑ 改善" },
  { "label": "被忽略学生数",       "a": 2,     "b": 0,     "delta": -2,    "trend": "↑ 改善" }
]
```

### 3.4 报告（report）

```json
{
  "scores": { "互动引导": 1.8, "提问质量": 2.1 },
  "strengths":   [ { "claim": "...", "evidence_turn_ids": [12, 13] } ],
  "improvements":[ { "claim": "...", "evidence_turn_ids": [31], "action": "下次提问后默数 3 秒" } ],
  "risk_flags":  [ "整节课 S2 从未被叫到" ]
}
```

## 4. 三人分工（按文件边界切）

> **切分原则**：每人拥有**独立的文件区域**，避免两人改同一个文件。这也是"能短分支高频合并"的前提。

| 角色 | 拥有的文件 | 负责的功能 | 交付物 |
|---|---|---|---|
| **P1 引擎** | `kj/students.py`、`kj/llm.py`、新增 `kj/lesson.py` | F1 教案解析、F2 学生生成、F3 实时对话、**F4 认知状态机** | 试讲引擎（AI 学生真的会说话） |
| **P2 数据与评价** | `kj/fias.py`、`kj/store.py`、`tools/` | F6 编码、**F7 指标计算**、F10 事件流与可重算、一致性比对工具 | 评价引擎 + 数据层 |
| **P3 前端与交付** | `web/`（新建）、`docs/` | F5 事件按钮、**F8 报告页**、F9 对比页、**F11 部署**、视频与材料 | 界面 + 可访问地址 + 比赛材料 |
| **共同承担** | — | 教案定稿、迷思概念库送审、**用户测试执行**、说明书统稿 | 知识资产 + 测试数据 |

**⚠️ 最容易没人认领的**：**内容与测试**。建议明确指定一人（通常是队长或表达最好的那位）为"测试与材料负责人"，**并把他的代码任务减到最少**。

## 5. ★ 分支与协作规则（对"两条长分支最后合并"的修改）

### 为什么不用"两条分支、最后合并"

1. **集成问题会在第 24 天才暴露** —— 那时只剩 2 天，来不及修；
2. 分支活得越久，冲突越难解，这是概率问题不是细心问题；
3. 3 个人不需要那么重的流程，**越早合并越安全**。

### 采用：主干可运行 + 短分支（1~3 天合一次）

```
main  ●───●───●───●───●───●    ← 永远能跑；每人做完一件事就合回来
        \   \       \   \
         ●   ●       ●   ●      ← feat/xxx 短分支，活 1~3 天
```

**四条硬规则**：

1. **`main` 必须永远能跑**：合并前**先 `git pull`，本地跑通 `python tests/test_fias.py`**，再合。
2. **短分支命名**：`feat/学生状态机`、`fix/走神频率`、`docs/分工文档` —— 一件事一个分支，**1~3 天内合掉**。
3. **前端不等后端**：契约（第 3 节）已固定，前端**用假数据先把页面做出来**，后端好了直接换数据源。
4. **最后 3 天（10/15 起）冻结代码**：只改材料和修 P0 级 bug，不加功能。

### 每天 5 分钟同步（比任何流程都管用）

群里发三行：
```
昨天做了：___
今天做：___
卡在：___（没有就写"无"）
```

## 8. 变更规则（怎么加需求）

1. **不砍掉 11 项必做里的任何一项**；
